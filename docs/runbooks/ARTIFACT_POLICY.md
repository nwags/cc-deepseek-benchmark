# Artifact Policy

This document defines which files are committed, generated, archived, ignored, or forbidden.

The repository contains both code and benchmark evidence. Raw benchmark artifacts are valuable for reproducibility, but they can be large and noisy. This policy keeps phase outputs organized and prevents accidental secret leakage.

## Artifact categories

### Source files

Source files are hand-authored or maintained files required to run, understand, or extend the benchmark.

Examples:

```text
README.md
AGENTS.md
Makefile
pyproject.toml
uv.lock
scripts/
scripts/lib/
configs/
docs/
.env.example
.gitignore
.export-ignore
```

These should generally be committed.

### Raw benchmark outputs

Raw benchmark outputs are produced by Harbor and Claude Code during canary, smoke, or full scored runs.

Examples:

```text
results/phase1/raw/
results/phase2/raw/
results/phase3/raw/
results/phase3/smoke/
results/phase3/canary/
```

These may include:

```text
result.json
trial.log
config.json
agent/claude-code.txt
agent/trajectory.json
verifier/reward.txt
verifier/test-stdout.txt
verifier/ctrf.json
agent/sessions/
```

Raw outputs are useful for reproducibility and qualitative analysis. For frozen phases, enough raw outputs should be committed or otherwise clearly archived so aggregates can be audited.

### Aggregate outputs

Aggregate outputs are phase-level scorebooks generated from raw outputs.

Canonical aggregate path:

```text
results/<phase>/combined.csv
```

Examples:

```text
results/phase1/combined.csv
results/phase2/combined.csv
results/phase3/combined.csv
```

These must be committed for any completed/frozen phase.

### Supplemental outputs

Supplemental outputs are generated tables, summaries, or intermediate analysis files.

Examples:

```text
results/phase1/supplemental/summary_metrics.csv
results/phase2/supplemental/failure_modes.csv
results/phase3/supplemental/router_observed_models.csv
results/phase3/supplemental/trial_summaries.jsonl
```

Commit supplemental outputs when they are used in reports or useful for reproducibility.

### Figures

Figures are generated charts used by reports.

Examples:

```text
figures/phase1/success_rate.png
figures/phase2/phase2_success_rate.png
figures/phase3/router_success_rate.png
```

Commit figures used in reports, unless the report-generation workflow clearly regenerates them.

### Reports

Reports are the primary deliverables.

Examples:

```text
docs/reports/phase1/REPORT.md
docs/reports/phase1/analysis.md
docs/reports/phase1/FINDINGS.md

docs/reports/phase2/PHASE2_REPORT.md
docs/reports/phase2/analysis.md

docs/reports/phase3/
```

Markdown reports should be committed. PDFs may be committed when they are deliverables, but Markdown remains the editable source of truth unless explicitly stated otherwise.

### Temporary snapshots

Snapshot files are conversation/review artifacts, not project source.

Examples:

```text
snapshot_v*.md
phase*_snapshot_v*.md
```

Do not commit snapshot files unless explicitly requested for archival purposes.

## What must be committed

For each frozen phase, commit:

* phase plan or report explaining the experiment
* run/config files required to reproduce the phase
* task list used for the phase
* raw Harbor outputs or a clearly documented archive strategy
* `results/<phase>/combined.csv`
* supplemental CSVs used in reports
* report Markdown
* figures used by report Markdown/PDF
* any script needed to regenerate aggregates
* artifact policy/runbook updates if paths changed

Minimum expected for Phase 1:

```text
results/phase1/combined.csv
results/phase1/raw/
docs/reports/phase1/
figures/phase1/
```

Minimum expected for Phase 2:

```text
results/phase2/combined.csv
results/phase2/raw/
results/phase2/smoke/
results/phase2/canary/
docs/reports/phase2/
figures/phase2/
```

Minimum expected for Phase 3 once complete:

```text
results/phase3/combined.csv
results/phase3/raw/
results/phase3/smoke/
results/phase3/canary/
docs/reports/phase3/
figures/phase3/
```

## What may be archived instead of committed

Large artifacts may be archived externally if repo size becomes unreasonable, but the archive strategy must be documented.

Candidates for external archive:

* full raw result directories for very large phases
* full Claude Code session directories
* generated PDFs if Markdown is committed
* intermediate scratch outputs
* duplicate raw logs not needed for auditability

If externally archived, document:

* archive location
* checksum if available
* date generated
* phase
* command used to generate
* relation to `combined.csv`

## What should be generated, not manually edited

These should be generated by scripts when possible:

```text
results/<phase>/combined.csv
results/<phase>/supplemental/*.csv
figures/<phase>/*.png
trial summary JSONL files
```

Do not manually edit aggregate CSVs unless explicitly documenting a correction.

## What must never be committed

Never commit:

```text
.env
.secrets/
*.env with real keys
real API keys
real auth tokens
credentials
private account IDs not required for reproducibility
.venv/
__pycache__/
.pytest_cache/
.DS_Store
local scratch files
snapshot files unless explicitly requested
```

Expected ignored secret paths:

```text
.secrets/anthropic.env
.secrets/deepseek.env
.secrets/gemini.env
.secrets/openai.env
.secrets/xai.env
.env
```

## API key examples

It is acceptable to include incomplete examples such as:

```text
ANTHROPIC_API_KEY=sk-ant-...
DEEPSEEK_API_KEY=sk-...
```

It is not acceptable to include complete keys or tokens.

## Smoke and canary artifacts

Smoke and canary runs must remain separate from full scored sweeps.

Use:

```text
results/<phase>/canary/<arm>/
results/<phase>/smoke/<arm>/
```

Do not aggregate smoke/canary rows into:

```text
results/<phase>/combined.csv
```

unless the file is explicitly named as smoke/canary-only, such as:

```text
results/<phase>/smoke-combined.csv
```

## Raw Harbor output policy

Raw Harbor outputs are important because they support:

* aggregate regeneration
* observed model verification
* failure-mode review
* transcript-level qualitative analysis
* debugging provider/router failures

For completed phases, preserve enough raw outputs to re-derive the aggregate.

For future very large phases, it is acceptable to store compact trial summaries in Git and archive full raw outputs elsewhere, but that change must be documented before the phase is frozen.

## PDF policy

Markdown is the editable source of truth.

PDFs may be committed when needed for sponsor delivery or assignment submission.

Rules:

* Generate PDF from reviewed Markdown.
* Do not hand-edit PDF content independently from Markdown.
* If a PDF differs from Markdown, document why.
* Keep phase-specific PDFs under the relevant report directory.

Examples:

```text
docs/reports/phase1/REPORT.pdf
docs/reports/phase2/PHASE2_REPORT.pdf
```

## Before committing artifacts

Run:

```bash
make check
make secret-scan
git status --short
```

Inspect staged files:

```bash
git diff --cached --stat
git diff --cached --name-only
```

Look specifically for:

```text
.env
.secrets/
snapshot_*.md
phase*_snapshot_*.md
.venv/
__pycache__/
unexpected root-level CSVs
unexpected raw results in the wrong phase
```

## Phase freeze checklist

Before declaring a phase frozen:

* [ ] Full scored aggregate exists at `results/<phase>/combined.csv`.
* [ ] Raw outputs are committed or archive policy is documented.
* [ ] Smoke/canary outputs are separate.
* [ ] Supplemental outputs used by reports are committed.
* [ ] Report Markdown is committed.
* [ ] Figures referenced by report Markdown exist.
* [ ] Reproduction commands are in the runbook.
* [ ] Secret scan passes.
* [ ] README points to the phase report and results.
* [ ] Later-phase plans are not mixed into scored results.
